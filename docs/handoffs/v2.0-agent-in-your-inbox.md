# v2.0 "Agent in your inbox" — Handoff

## Outcome

- Result: All 16 milestone issues (#97–#112) implemented, tested, and documented.
- User-visible effect: The bot now writes full natural-language replies (no deterministic templates), uses progressive disclosure (compact core prompt + on-demand capability docs), supports weekly summaries, food-history search, and user-scoped custom food aliases. Tool modules are split into focused files with a central registry.
- Status: complete — ready for user's final review before merging v2.0 into master.

## Scope and decisions

- In scope: Issues #97–#112 (all v2.0 milestone issues).
- Out of scope: Dynamic tool routing (deferred to post-v2.0 per ADR 0007). Java sister repository (independent build path). Live OpenAI eval runs (require API budget and isolated DB; fixture structure is validated by unit tests).
- Key decisions:
  - Progressive disclosure: core prompt (~15 lines) + 7 capability markdown docs loaded via `load_instructions(topic)`.
  - Model writes full replies from structured tool results; deterministic templates removed.
  - `context.romanian` removed; model decides language.
  - Tool modules split: `journal_actions.py`, `nutrition.py`, `planning.py`, `settings.py`, `instructions.py`, `aliases.py`, `shared.py`, `registry.py`.
  - Food aliases use a stored generated column (`alias_lower = lower(alias)`) for case-insensitive uniqueness with atomic ON CONFLICT upsert.
  - Adversarial review findings B1, H1, H2, H3, M1, L1, L2 fixed; M2 (broad transaction pattern) noted as residual risk.
- Assumptions:
  - The dev/test database is the only environment with applied migrations; production will receive both migrations (`a1b2c3d4e5f6` and `b2c3d4e5f6a7`) in sequence.
  - The eval fixture file (`text-journal.json`) is the authoritative scenario list; live model eval is run manually with `TERMINAL_EVAL_FILE`.

## Adversarial review

- Cases attempted: ownership isolation, case-variant duplicates, non-string args, boolean calories, control characters in canonical name, overly long strings, empty/missing fields, out-of-range calories, mutual exclusion of calorie fields, cross-user resolve.
- Findings:
  - B1 (blocker): Case-sensitive unique constraint allowed case-variant duplicates → FIXED with generated column + case-insensitive constraint.
  - H1 (high): Non-atomic upsert race condition → FIXED with ON CONFLICT upsert.
  - H2 (high): No string type/length validation → FIXED with isinstance check and length limits.
  - H3 (high): Boolean calories accepted → FIXED with explicit bool rejection.
  - M1 (medium): No DB-level check constraints → FIXED with CHECK constraints in migration.
  - L1 (low): No schema string length limits → FIXED with minLength/maxLength in tool schemas.
  - L2 (low): Control characters in canonical name → FIXED with regex validation.
  - M2 (medium): Broad transaction commit pattern in inbox_worker → NOT FIXED (pre-existing pattern affecting all tools, not alias-specific; noted as residual risk).
- Regression coverage added: 5 new adversarial tests in test_food_aliases.py (non-string alias, boolean calories, control characters, overly long alias, case-variant duplicate prevention).
- Residual risks:
  - M2: The `process_one` pattern in `inbox_worker.py` commits the session after both success and exception paths. A failed turn may still persist tool side-effects. This is a pre-existing pattern affecting all tools, not specific to aliases. Fixing it requires a broader transaction-boundary refactor.
  - Live model eval not run: The eval fixture structure is validated by unit tests, but live OpenAI calls require an API budget and isolated database. Run `TERMINAL_EVAL_FILE='app/terminal/fixtures/text-journal.json' TERMINAL_EVAL_REPEATS=3 python -m app.terminal.repl` manually before production release.
  - L3: `list_by_user` in food_alias_repo is currently unused; kept for future use.

## Review fixes (post-handoff)

Three issues found during review and fixed:

1. **`load_instructions` enum missing `aliases`**: The system prompt advertised an `aliases` capability index entry, but the `load_instructions` tool's `topic` enum did not include `"aliases"`, so the OpenAI API would reject any `load_instructions(topic="aliases")` call. Added `"aliases"` to the enum in `tool_schemas.py` and added a regression test.
2. **`portions.md` referenced non-existent `compute_portion` tool**: The portions capability doc told the model to use a `compute_portion` tool that does not exist in the registry or tool definitions, which would cause production failures when the model tried to call it. Rewrote `portions.md` to instruct the model to compute fractions itself with basic arithmetic. Updated `test_load_instructions.py` to assert the doc does not reference unknown tools.
3. **Dead `is_romanian` import**: Removed the unused `from app.agent.language import is_romanian` import from `journal_application_service.py` (the function is still defined in `app/agent/language.py` for future use, but no longer imported in the service).

Additionally cleaned up 30 unused imports and 2 nested-if style issues across the v2.0 tool modules (pre-existing leftovers from the refactor) via `ruff --fix` and manual edits. Restored `_resolve_meal_instant` as a re-export in `journal_tool_executor.py` with `# noqa: F401` because tests import it from that module.

Final verification: 94 unit tests + 72 integration tests pass (166 total), `ruff check app tests` clean.
